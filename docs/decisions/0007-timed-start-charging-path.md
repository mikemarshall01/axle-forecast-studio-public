# Decision 0007: optional timed-start charging path

Status: accepted by the lead on 8 October 2026, from Mike's request to see what a simple "home charging may only commence from a set clock time" rule does to the fleet, beside Unmanaged and Smart.

A third reported path, `timed` ("Timed tariff"), is the unmanaged rule (plug in and charge at full device power to the preferred target, whole connected slots only) except that home charging is held off in a daily London wall-clock stretch from 12:00 (the existing session-night boundary, `clock.STUDY_START_LOCAL_HOUR`) until an editable start time `T` (`timed_start_local_hour`, London clock hours, 0-23.5 in half-hour steps, default 0.0 = midnight), gated by a separate on/off switch, `timed_tariff_enabled` (default on). It is named for the common real-world pattern of a timed tariff, but no tariff price is modelled and every path is costed the same way; the wording must never imply otherwise. Hard rule: no fallback and no spill into an allowed half-hour, so a session that cannot fill in time simply leaves short, exactly as a timer-only home charger would; it tops up publicly like any other short session. The rule runs over the whole simulated run, warm-up included, so the study opens from timed batteries, and it draws no new random number: the third pass reuses the same sampled inputs as normal and selected (common random numbers).

Display order (lead decision, 8 October 2026): on screen the three paths read Unmanaged, Timed tariff, Smart (`style.PATH_DISPLAY_ORDER`), so the new path sits between the two it is compared against rather than trailing both; the frames and `model/forecast.PATH_ORDER` keep the kernel's own normal/selected/timed order, since that is what the third, paired pass actually reports.

Present by default, start 00:00 (Mike's decision, 8 October 2026, superseding the original off-by-default choice above). `timed` appears in `fleet_world_intervals`, `cohort_world_intervals`, `fleet_interval_bands` and `cohort_interval_bands`, and as a third P10-P90 line on the Smart charging ▸ Response chart, styled with an existing non-teal token (`style.SERIES_COLOURS["difference"]`'s value, dashed): teal stays reserved for the smart (selected) path. The path is present when the "Timed tariff policy" switch (`timed_tariff_enabled`) is on (the default) at the set start time, absent when off, because a bounded `number_input` has no reachable "unset" value in Streamlit: switched off, every result and screen is unchanged from before this decision. At this original point in the decision, costs, savings, zones, charge completion, session distribution and household outcomes for the timed path were explicitly out of scope: they needed the per-EV chunk pass and the cost frames to learn a third path, which model step 2 below adds. Trading, supplier, firm-MW availability, run comparison and the other strictly pairwise frames step 2 lists stay normal versus selected throughout, with or without step 2; `timed` never enters the trading overlay, with or without step 2 either.

## Model step 2 extension (lead decision, 8 October 2026)

The scope above is extended: the frames and functions below also learn the optional timed path, following the same rule throughout — a frame that already carries `path_id` gains an optional `timed` row; a wide frame gains optional `timed_*` columns; a pairwise normal-versus-selected frame gets a sibling built by the same function with `timed` in the selected slot. Nothing is restructured and no new random draw is added (the timed pass still reuses the normal and selected pass's sampled inputs). Every item not listed here stays strictly normal versus selected, named explicitly in the code (never picked up by iterating a shared path list): trading, supplier P&L, firm-MW availability and product frames (`settlement_file`, `product_sheet`, `firmness_by_manufacturer`, `manufacturer_summary`), battery cycles, carbon shift, partner frames, hedge blocks, intraday dispatch, events, flexibility bands, run comparison, `fleet_interval_ev_bands`, `weekly_bands` and `average_day_bands`.

- **Kernel.** `physics.simulate_fleet_intervals` now tracks the timed path's per-zone sums (`zone_sums.study["timed"]`) whenever both `zone_sums` and `timed_start_allowed` are given, so the zone frames below can report it; it still never enters the trading overlay. `physics.simulate_unit_intervals` accepts the same `charge_allowed` mask `_simulate_path` already takes, so the per-EV chunk pass can simulate the timed path too.
- **Per-EV pass.** `summaries.kernel_slice` takes `path_id` (`"normal"`/`"selected"`/`"timed"`) instead of a `selected` bool; `summaries._per_ev_chunks` simulates the timed path as a third pass per chunk when asked, reconciled against the fleet frame like the others (`summaries._check_reconciles`). This is the one extra per-EV kernel pass per chunk the setting on adds; every consumer below reads it from that one pass rather than re-simulating.
- **Zones** (trading contract v1 §5.6-§5.8). `zone_world_intervals`, `zone_import_bands` and `zone_summary` gain a `timed` row/path wherever the run has it, read from `zone_sums.study["timed"]` above.
- **Charge completion** (§10.5e). `charge_completion_summary` gains a `timed` `path_id` block (same `group_id`/`departure` rows) when the run completes the timed path; `product.new_totals`/`accumulate` take the active `path_ids` rather than a fixed two.
- **Session distribution** (contract 3.10c). `session_distribution_bands` gains a `departure_soc_percent_timed` metric (same bin spec as `departure_soc_percent_smart`) only when the run has the timed path; `session_values`/`session_distribution_rows` take an optional `timed_closing_kwh`.
- **Smart charging outcomes** (contract 4.4-4.6). `smart_charging_world`/`smart_charging_summary` gain a `timed_average_price_gbp_per_mwh` column/metric (the price-paid KPI), with no "change" reading of its own. `weekly_peak_summary` and `price_band_shift` already looped over a path order; model step 2 makes that order the one the run's own frame actually carries (normal, selected, optionally timed), so `price_band_shift` also gains `timed_kwh_p10/p50/p90` columns.
- **Cost** (contract 4.8-4.9a). `action.calculate_wholesale_world_cost_effect` takes `selected_path_id` (default `"selected"`); the forecast runner calls it a second time with `"timed"` to produce `timed_cost_effect`, and `summaries.cost_effect_summary`/`not_recovered_summary` (unchanged functions) build `timed_cost_effect_summary`/`timed_not_recovered_summary` from it. Same prices, same public rate, same shortfall valuation as the ordinary cost effect, so the two savings are directly comparable.
- **Household** (household contract v1 §3.1-§3.2). `household.new_totals`/`accumulate`/`build_frames` take the active `paths`; `household_ev_world` gains `*_timed` columns in the existing per-path naming pattern (`home_import_kwh_timed`, `cheap_import_kwh_timed`, `home_cost_gbp_timed`, `public_cost_gbp_timed`, `public_import_kwh_timed`, `completed_count_timed`, `departure_soc_mean_timed`) and `household_outcomes_summary` gains the matching metrics (`home_cost_gbp_per_kwh_timed`, `home_import_kwh_per_week_timed`, `public_import_kwh_per_week_timed`, `cheap_share_timed`, `completed_share_timed`, `departure_soc_mean_timed`). No "timed vs normal" difference metric: differences stay §3.2's own selected vs normal. CO2 shift, nights plugged and sessions-affected stay normal versus selected only. The household card's `one_ev_arrays`/`build_card` are unchanged (out of scope: see the model-step-2 handoff for why).
- **One-EV replay** (replay contract v1 §2, contract v2 §5). `individual._paths` adds `"timed"` when the result's fleet frames carry it; `individual._one_ev_kernel_frame` passes the run's `timed_start_allowed` mask into the same `simulate_fleet_intervals` call that already computes normal and selected, so `OneEvReplay.intervals`/`plug_events`/`daily_audit` and `OneEvTimeline.cumulative` gain the timed path with no extra kernel pass.

The policy is on by default (`timed_tariff_enabled`, start `0.0`, midnight), so a default-size run carries the timed path unless a user switches it off. That does not alter anything above: `assumptions.forecast_inputs` passes the start hour to the model when the switch is on and NaN when it is off, and every frame and function here keys off whether the run's `timed_start_local_hour` is set, not off a particular default value.
